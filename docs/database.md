# Fabric database and node registry

The first production database milestone is `fabric.nodes`, with exactly four
columns: `uuid` (UUID primary key), `id` (unique positive INT8), `region`, and
`zone`. No automatic timestamps or embedded `gorm.Model` fields are present.
`id` is the existing Ansible integer and is never generated by this database.
Reuse the existing backend UUID and placement values when importing known nodes.

`control/internal/database` uses GORM with the PostgreSQL/pgx driver.
Gormigrate records applied version IDs in `schema_migrations`. Migration
`202610250001_nodes` contains immutable DDL; it does not depend on the current
Go model or run AutoMigrate against application models. Unknown recorded
migrations fail validation. Complete migration transactions retry SQLSTATE 40001.
Run one migration process at a time. No migrations run during agent startup.

```sh
# Set FABRIC_DATABASE_URL securely using an operator identity.
# Require sslmode=verify-full and sslrootcert=/mounted/ca.crt.
go run ./control/cmd/fabric-db -migrate
go run ./control/cmd/fabric-db -import-nodes /private/nodes.json
go run ./control/cmd/fabric-db -list-nodes
```

Every connection uses IPv6, including endpoints supplied as DNS names. Server
certificate verification is mandatory. Neither the DSN nor SQL parameters are
logged. CA paths belong to the machine/container running the command.

Node imports are atomic and additive. A matching UUID/ID pair permits placement
updates. Remapping either identity to an existing different identity fails the
whole batch. Missing nodes are retained. Import JSON contains only `uuid`, `id`,
`region`, and `zone`.

Use an operator identity for provisioning and migrations. The dedicated runtime
SQL user `fabric` needs only:

```sql
GRANT CONNECT ON DATABASE fabric TO fabric;
-- Run the following while connected to the fabric database:
GRANT USAGE ON SCHEMA public TO fabric;
GRANT SELECT, INSERT, UPDATE ON TABLE nodes TO fabric;
```

For a new dedicated database, revoke public database/schema privileges before
granting these permissions. Do not grant runtime users ownership, admin,
CREATE, DELETE, migration-history access, or access to the dn42 database.
Generate a separate strong password and keep it in operator secret storage;
do not put operator credentials in the runtime configuration.

RuntimeInstance persistence remains deferred. The previous inventory SQL is
embedded only in the opt-in test fixture. `inventoryd` cannot migrate it and
must not be enabled against this nodes-only database. A future versioned
migration must reference `nodes.uuid` and keep observation freshness/ordering
outside this four-column identity model.

Validation uses the existing opt-in secure IPv6 CRDB/NATS lab: migration replay,
exact columns, identity conflict rollback, placement updates, runtime DML and
negative privilege checks. The shared fixture also tests inventory transport
and reconciliation independently from the new production schema.
